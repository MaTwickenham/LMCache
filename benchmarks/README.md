# TTFT Benchmark Spec

This document defines the canonical Time-To-First-Token benchmark settings for
LMCache under `benchmarks/blend_ttft`.

The goal is to keep TTFT measurements aligned with the target workflow:

1. Reusable KV comes only from offline fragment-prefill.
2. Online query TTFT includes query-time lookup / retrieve / injection
   overhead.
3. Online query TTFT does not include saving new KV generated by that query
   back into the fragment pool.
4. Inter-query pool maintenance is a separate concern and must not be mixed
   into online TTFT unless a benchmark explicitly says so.

Concrete CLI wiring is expected to be handled by shell scripts. Do not rely on
per-script defaults for headline TTFT experiments.

## Canonical Scope

All canonical TTFT experiments should be built on top of
`benchmarks/blend_ttft`.

Use the following benchmark paths by intent:

- `benchmark_explicit_fragments.py`: canonical TTFT benchmark path for
  explicit fragment-pool semantics, utility gating, and separated maintenance.
- `run_pareto_gpu_pool.py`: budget sweep helper for Pareto-style plots.
- `compare_prefix_vs_blend_cpu.py` and related CPU wrappers: synthetic or
  diagnostic microbenchmarks, not the canonical real-workload TTFT path.

## Shared Settings

The following settings should be treated as the benchmark-wide contract unless a
specific experiment explicitly states otherwise.

- `skip_save = True` for online query requests.
  Reason: the benchmark models a workflow where only offline fragment-prefill
  produces reusable KV cache objects. Online query KV writeback must not
  contribute to TTFT.
- `fragment_order_policy = auto`.
  This resolves to `profile_last` for `memoryos` and `trace` for other current
  workloads.
- `prefill_order_policy = sorted`.
  This is the canonical offline materialization order.
- `chunk_size = fixed`.
  Chunk size must be held constant within one comparison set. Chunk-size
  ablations should be reported separately.
- `max_tokens = 1`.
  TTFT benchmarks always generate one token.
- Warmup is allowed but must never be counted in reported TTFT.
- Prompt assembly and workload construction should be identical across methods
  for the same comparison.

## Method Profiles

Each TTFT method should be mapped to one of the following method profiles.

### 1. `recompute`

Pure compute baseline with no cache reuse.

- Engine path: plain vLLM
- Prefix caching: off
- Blend: off
- Online execution mode: not applicable
- `skip_save`: not applicable
- `admit_misses_to`: off / not applicable

### 2. `prefix`

Native vLLM exact-prefix reuse baseline.

- Engine path: plain vLLM
- Prefix caching: on
- Blend: off
- Online execution mode: not applicable
- `skip_save`: not applicable
- `admit_misses_to`: off / not applicable

### 3. `cacheblend_legacy`

Original CacheBlend-style baseline.

- Engine path: LMCache blend path
- Connector: `legacy`
- Fragment backend: CPU-only
- Online execution policy: fixed
- Online execution mode: `blend`
- `skip_save = True` on online query requests
- `admit_misses_to = none`
- Legacy lookup / retrieve path should be used for this baseline

This profile is meant to represent the original heavy-overhead CacheBlend-style
runtime rather than the optimized path.

### 4. `ours`

Optimized fragment-reuse runtime with utility-guided online choice.

- Engine path: LMCache blend path
- Connector: `fast`
- Lookup / retrieve: sparse blend path
- Online execution policy: `utility`
- Execution choice: utility model dynamically selects between:
  - `blend`
  - recompute / native-vLLM bypass
- `skip_save = True` on online query requests
- `admit_misses_to`: enabled
- `admit_misses_to` is expected to become utility-coupled over time

This profile is the canonical method for reporting the optimized system.

## Settings That Are Method-Specific

The following settings should not be silently shared across all methods.

- `execution_mode`
  - `ours`: selected dynamically by the utility model
  - `cacheblend_legacy`: fixed to `blend`
  - `prefix` / `recompute`: handled by the plain-vLLM baseline path
- `legacy` vs `fast`
  - `ours`: `fast`
  - `cacheblend_legacy`: `legacy`
- `lookup / retrieve`
  - `ours`: sparse lookup / optimized retrieve path
  - `cacheblend_legacy`: original path
- `admit_misses_to`
  - `ours`: enabled
  - all baselines: disabled

## Important Clarifications

### `fragment_order_policy`

This controls the order of reusable fragments inside each query prompt.

- It changes prompt shape.
- It changes prefix-caching opportunity.
- It changes how dense or sparse fragment reuse looks to CacheBlend.

Canonical value: `auto`.

### `admit_misses_to`

This controls whether fragments that missed in the current query are admitted to
the fragment pool after the query finishes.

- It is a pool-maintenance control-plane setting.
- It only makes sense on the explicit fragment-pool benchmark path.
- It should be disabled for baselines.
- It should be enabled for `ours`.
- Its overhead must not be mixed into online TTFT unless the benchmark
  explicitly says it is measuring end-to-end cycle time rather than online TTFT.

## Recommended Reporting Rules

For TTFT headline tables and figures:

- Report online query TTFT.
- Keep offline fragment-prefill preparation separate.
- Keep inter-query maintenance separate.
- Keep chunk-size sweeps separate from main method comparisons.
- Keep budget sweeps separate from fixed-budget headline comparisons.

If a result mixes online TTFT with maintenance or online save/writeback, it must
be labeled as a different metric and must not be called canonical TTFT.

## Script Guidance

Shell scripts should pass these settings explicitly.

Recommended practice:

- Do not depend on parser defaults for canonical experiments.
- Treat method profiles as named configurations in shell.
- When adding a new workload, keep the shared settings unchanged unless there is
  a workload-specific justification documented alongside the script.

## Future Work

The current benchmark contract already reserves one future extension:

- `ours` should eventually couple `admit_misses_to` with the utility model
  rather than leaving it as a static policy knob.

When that is implemented, update the shell profiles to reflect the exact
admission rule, but keep the high-level benchmark contract unchanged.
